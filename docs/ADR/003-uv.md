# ADR 003 — uv e escopos Python

Status: adotada em 2026-11-03; ampliada em 2026-11-05 para ambiente pessoal opcional.
Para as CLI Python do projeto, substituída pelo [ADR 004](004-lock-ferramentas-uv.md)
em 2026-11-09: elas não usam mais `uv tool`.

uv gerencia CPython do usuário, ferramentas CLI isoladas, dependências .venv de
cada projeto e execuções temporárias com uvx. Um quinto escopo opcional é o
ambiente pessoal `geral`, criado explicitamente pelo usuário para uso avulso.
Ele não reúne dependências dos projetos. Não usamos pip global, Python do
sistema como destino ou alteração global de UV_PROJECT_ENVIRONMENT.

Com uv e direnv selecionados e disponíveis, shells interativas selecionam o
ambiente pessoal existente em `$XDG_DATA_HOME/devshell/venvs/geral` (default
`~/.local/share`). Outra ativação manual ou Conda é preservada. O `.envrc`
autorizado de cada projeto usa `use devshell_python` para retirar o ambiente
anterior do PATH e selecionar a `.venv` local. Direnv restaura o ambiente
anterior ao sair. O helper não executa `activate`, cria ambientes ou sincroniza
dependências; sem `.venv` válida, aplica a retirada do ambiente anterior e avisa.
Uma configuração não autorizada continua bloqueada, sem detecção automática de
repositórios. Esse custo de preparação por projeto preserva a autorização
individual e evita downloads durante navegação.
Conda ativo também é preservado pelo helper, com aviso para desativação
explícita antes da troca, pois sua ativação mantém estado próprio na shell.

Interpretadores usam versões patch e --no-bin. CLI usam versões exatas e um
CPython gerenciado declarado. Bibliotecas científicas ficam num exemplo com
pyproject/lock e não entram no perfil science. O custo é atualizar manifestos
por revisão e validar wheels por plataforma; ter um lock não certifica GPU,
musl ou aarch64.
